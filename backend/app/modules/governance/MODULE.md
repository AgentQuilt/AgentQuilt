# governance

- Interface: one declared operation, `governance.decide_approval(approval_id, decision, reason)`, dispatched like any other write. It is unversioned on purpose: approvals are not a versioned aggregate, so the declaration names no `aggregate` (ADR-0017 allows none) and a caller passes no `expected_version`.
- Decision: only a `requested` approval moves; anything else returns `{"decided": false, "state": ...}` and still commits its own action, because the ledger records that the answer was given. Approve moves it to `open` with `granted_by` set to the deciding principal; reject moves it to `rejected` and stores the reason, which becomes the tool result when the parked call resumes.
- Decider: a principal of class `user` or `system` (ADR-0004). Anything else raises, and dispatch surfaces the raise as the tool failing; a denial event for it waits for the wave that gives modules a refusal path.
- Continuation: in the same transaction, a guarded `update(Run)` from `waiting_approval` to `queued` returning the id, and the `StepQueue` row for `(run_id, step_no)` only when that returned a row. A run that is absent, cancelled or already queued is decided and not enqueued (`run_queued` is false).
- Interface, second operation: `governance.undo_action(action_id)`, also unversioned and also decided from outside any run. It reads the action's `compensator_ref` and `compensator_args` — the recorded result of the call being undone — and refuses when there is no compensator, which is the registry's own statement that the operation was irreversible; the refusal carries the reason and still commits its action, because the ledger records that the reversal was asked for.
- Undo runs the compensator in a new run, never in this transaction: `runs.create` plus one steering message naming the compensator and its recorded arguments, so the worker makes the call under its own ceiling, its own approval gate and its own action. The run is created from the org's agent definition; Phase 1 seeds one.
- Lock order: `create` takes no lock, and `post` locks the run row before the mailbox row, so undo obeys the run-row mutex (`runs/MODULE.md`) like every other writer.
- Routes (`router.py`): `POST /approvals/{id}/decide` and `POST /actions/{id}/undo` are the two operations dispatched, not a second write path — the path id and the body become the declared args, and the `CallContext` carries `run_id=None`, so a decision comes from outside every run and carries no ceiling. A denial is 403 with dispatch's reason; the operation's own result, refusal included, is 200, because a refusal the ledger recorded is an answer and not an error.
- Not built: any read of the approval queue; expiring an approval, which is `runs.tick`'s and reaches the same continuation; compensation failure, partial reversal and the draft lifecycle, which stay open questions until the CRM slice declares its first external write (D3, 2026-08-30); and a denial event of the module's own, which waits for the wave that gives modules a refusal path.
