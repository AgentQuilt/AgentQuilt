# runs

- Interface: `create(session, agent_definition, skill_version, *, stage) -> Run`, `send(session, run_id, text) -> MailboxMessage | Ended | None`, `events(session, run_id, after_cursor) -> Sequence[Event]` and `cancel(session, run_id) -> bool`. Plain functions inside the caller's transaction, reading the org and the principal off the session the way `declare.ledger` does; no port, since Postgres is the only dependency.
- Ceiling: `create` computes ADR-0015's capability ceiling once and stores it on the row, so a run cannot widen later. Phase 1's intersection is `identity.effective_grants` for the originator plus the definition's memory scope.
- Stage: ADR-0012's one predicate at run start — a PROD run refuses a skill version that is not PROD-stage, and the violation is a `ValueError`, not a denial, because nobody is asking permission yet.
- Mailbox: `send` allocates `seq` under `SELECT ... FOR UPDATE` on the run row, so two senders serialise instead of colliding on `uq_mailbox_message_run_seq`. That lock is also the tenancy proof: row-level security hides another org's run, so the lock finds nothing and the call returns `None` having written nothing.
- Mailbox writes: `send` is `post(session, run_id, kind, body)` with the `steer` kind; the worker posts its `conflict` notices through the same allocator, so `seq` has one owner.
- Wake: the run row is locked before `seq` is allocated, so the state read under it is the state the message lands against. `queued`, `running` and `waiting_approval` take the message and the next drain picks it up; a `done` run takes it and wakes — the guarded `done -> queued` plus one `step_queue` row at `max(checkpoint.step_no) + 1`, the shape `tick._continue` uses, so state and queued work cannot disagree; `cancelled` and `failed` refuse, returning `ENDED` and writing no mailbox row, because nothing would ever drain it. Re-opening a cancelled or failed run is out of scope: a cancel is a person's decision and a failure needs eyes. The worker's `conflict` posts only target a run mid-step, so that path is untouched.
- Events: `events` is the run's ledger stream ordered by `Event.id`, and that id is the cursor the SSE route below resumes from.
- Routes (`router.py`): `POST /threads` starts a run on the org's latest agent definition, `POST /runs/{id}/messages` is `send` and answers 404 when the org has no such run and 410 ("the thread has ended") when the run is cancelled or failed, and `GET /runs/{id}/events` streams the ledger as SSE — one `ServerSentEvent` per row, its `id` the `Event.id` the client sends back as `Last-Event-ID`, so a reconnect resumes from the cursor and repeats nothing. The stream opens a session per poll rather than holding one open across a yield, and a run this org cannot see streams empty rather than 404, which is the same thing row-level security already says. Auth is `app/serve.py`'s two dependencies; no route here dispatches an operation.
- Cancel: D4 in one transaction — `state = cancelled`, the run's `step_queue` rows deleted, its `requested` and `open` approvals expired, and a `run_journal` event `run.cancelled`. No new event kind, no new table.
- Mapped: `step_queue`, `mailbox_message` and `checkpoint`, column for column with migration 0001, on the store's `Base` so the drift test reads them; `core.run` stays mapped in `store/models.py` and is imported, never mapped twice.
- Work (`work.py`): `claim(session, *, worker_id, now) -> Claimed | None` takes one free row under `SELECT ... FOR UPDATE SKIP LOCKED` on a lease and commits; `step(session, claimed, *, runner, registry, clock) -> str` then does the whole cycle in a second transaction — drain, `context.assemble`, `model.run`, journal the plan, dispatch, checkpoint, re-enqueue — and returns the run's state. ADR-0019: no model call inside a claim. `work_once(scope, ...)` is the pair of them, and the `work` role loops it.
- Step endings: `WaitingApproval` parks the run (`waiting_approval`, queue row deleted, no checkpoint, so the re-queued step drains and plans again) and journals a `run_journal` event `step.parked` naming the approval id and the operation, in the step's own transaction, because Phase 1 has no route that lists an open approval and the id has to reach the person watching the stream; a `version_conflict` denial and its `conflict` mailbox message land in the step's own transaction and the step carries on; `model.run`'s `Refused` is terminal (`failed` plus `failure_reason`, queue row deleted, no checkpoint); a turn that proposes no call ends the run `done`, which the run's state carries and no extra event repeats. Every ending lands through a state write guarded on the `running` the claim wrote, so a cancel that arrives mid-step is felt at the boundary: the run keeps `cancelled`, and neither checkpoint nor next queue row is added.
- Lock order: the run row is the lifecycle mutex. Every writer that moves a run's state or its queue rows takes the run row lock first — `claim` under `SKIP LOCKED`, `cancel` and the approval continuations through their guarded updates, a settling step through its guarded state write — so a cancel serializes with every requeue and no pair deadlocks. The approval row comes after the run row (`cancel` expires approvals under the mutex, the deciders and tick pre-lock the run before touching the approval). The step takes the mutex after its model call and before dispatch, so the approval rows it creates or reads sit under it and a cancel waits only for the dispatch-and-settle tail, never for a model. A step never locks a foreign run row: deciding an approval from inside a run is refused (ADR-0004 and this order), so no two workers can hold each other's mutex.
- Drain: the last checkpoint's `mailbox_seq` is the watermark, so a step worked again after a crash sees exactly what the crashed one saw. Until `surfaces` owns D5 and D6, the drained messages are rendered into `Call.intake` as one `[kind] text` line each, oldest first.
- Transcript: the worker is D4's producer (ADR-0006 and ADR-0027 list the slot; nothing filled it before). `step` renders `Call.transcript` from rows the run already has — the mailbox messages with `seq <= watermark`, interleaved with what the agent said at each worked step, read off the `step.planned` events — one `[person]` / `[agent]` line each, a non-steer message keeping its kind tag, and a step worked twice keeping the plan that settled it. The watermark is both the drain's floor and the transcript's ceiling, so no message is ever in D4 and D6 of the same turn, and a first step has no checkpoint and so no transcript. No stored transcript, no new event kind: the rows exist.
- Expected version: nothing hands the model one in Phase 1, so the step reads the aggregate's stream head as it dispatches (ADR-0017); a step that loses the race gets dispatch's conflict denial.
- Tick (`tick.py`): `tick_once(scope, *, clock) -> Pass | None`, a leader under `pg_try_advisory_xact_lock` — clear leases past their expiry, then expire every `requested` approval past `expires_at` in a transaction each: `requested -> expired`, the guarded `waiting_approval -> queued`, and the `step_queue` insert only when that guard returned a row.
- Not built: child runs (`parent_id`), narrowing state, pinned workers (ADR-0018's claim predicate waits for the browser-relay class), any queue tag other than `main`, retries and backoff, and a worker heartbeat.
- Tests, against a real Postgres: `tests/test_runs.py`, whose mailbox test uses two sessions on two connections because the thing under test is a row lock; and `tests/test_work.py`, which drives the work functions rather than the CLI loop — one step end to end, a crash replayed under the same reservation keys, a cancel felt at the step boundary, an approval nobody answered, and a woken run whose D4 holds the earlier turns while D6 holds only the fresh one.
