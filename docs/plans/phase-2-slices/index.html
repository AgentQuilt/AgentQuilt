D1: The front-end stack — one-time, before the first screen Settled 2026-08-31

What you said: Phase 2 works front-end and back-end together; slice 1 carries "the one-time front-end foundation (stack, tokens, Biome/tsc gates)". The stack itself was never recorded as a decision. D2: The four new chat routes — kernel routes or declared operations? Settled 2026-08-31

What you said: (via the settled structure) "one declared operation surfaces as agent tool, HTTP route and UI action alike" (system-structure.md:84) — the scout flagged that the new routes could be read as owing that path. What we might be missing: if a later surface wants agents themselves to browse threads, that read becomes an operation then — additive, no migration. Cost if wrong: four route bodies move behind declarations later; the URL surface stays.

5The environment rail — what migration 0003 lands and the shape choices inside it

These are the taste calls the scouts flagged as unrecorded, decided here so the wave briefs are executable; each is correctable at review before its wave lands. The one-line frame: content is org-global, activity is environment-scoped, and pointers connect them.

  • The Environment row (core.environment): id, org_id, key ("dev", "prod"), kind (dev | prod), protection_level, created_at; unique (org_id, key) and UNIQUE (org_id, id) — the second is the referenced pair every composite scope FK below points at, which Postgres requires to be unique. Seeded two planes per org (ADR-0028 D2's small-org default); three is an insert, not a migration.
  • Environment-scoped (gain environment_id, RLS keys on both): run and its five children (step_queue, mailbox_message, checkpoint, context_manifest, usage_record), approval, event, action, stream_head, idempotency_key (its PK grows the new column — a DEV replay must not eat a PROD reservation), and the new skill-binding table below.
  • Org-global, deliberately (no environment column): user, principal, user_token, role, grant, org itself — people and their permissions span planes; "who may touch PROD" is the Environment row's protection_level enforced at promotion, not a second grant system. And the artifacts: skill, skill_version, agent_definition stay org-global — a version is content; which version an environment runs is the env-scoped pointer. This also dissolves the scout's FK contradiction: the run → skill_version cross-schema FK never crosses environments because the version row has no environment.
  • Promotion becomes a pointer flip: a new mod_skills.skill_binding row per (org, environment, skill) naming the active version, org- and environment-scoped under the same two-key RLS as the rest of the rail. SkillVersion.stage and its mutate-under-lock promotion (premise 7) are replaced; activate_version keeps its name, declaration and compensator story but flips the binding row — ADR-0028 D5's immutable-artifact shape, receipted exactly as today.
  • The session pins one environment: a third GUC beside org and principal (app.environment_id), set by store.session(); RLS on env-scoped tables fails closed when it is unset, mirroring the org predicate. Scope becomes (org, environment, principal) and tenants() yields the pairs, so work and tick iterate planes the way they iterate orgs today. The two recorded RLS bypasses (tenants(), resolve()) keep their dated-workaround entries, and E1 adds one narrow third of the same class: locate(kind, id), the scope-pair read an identifier-addressed HTTP call (run, approval or action id) needs before it can open its environment-scoped session (detail in wave E1).
  • The run pins at start: run.environment_id replaces run.stage; run.tier_binding_version pins the model binding at create (the capability_ceiling precedent — computed once, never widened), and context.assemble reads the pin instead of the latest row, which is what makes a binding bump promotion-safe for new runs only (ADR-0028 D5).
  • Scope-carrying FKs (ADR-0028 D2), three constraints deep so the pair is impossible to fake, not merely filtered: every env-scoped table's (org_id, environment_id) is a composite FK onto core.environment (org_id, id) — the pair must name a real plane of the same org; env-scoped parents gain UNIQUE (org_id, environment_id, id) and every FK between two env-scoped rows becomes composite on (org_id, environment_id, referenced id) — the five run children, run.parent_id, the ledger pair (action.event_id and the deferred event.action_id), stream_head.last_event_id, idempotency_key.action_id, and approval's references — so no row points across planes; and skill_binding's version reference is the composite (skill_id, skill_version_id) onto skill_version (skill_id, id) — backed by a new UNIQUE (skill_id, id) on skill_version in the same migration, since its primary key alone cannot satisfy the composite FK — so a binding cannot pair one skill's row with another skill's version.
  • Thread create names its plane: POST /threads takes an optional environment key, defaulting to the org's prod plane; the harness page grows a selector so QA lives on dev without touching prod data.
  • ADR upkeep in the same waves: ADR-0008's "org_id and nothing else" line is amended by the wave that changes the policies; ADR-0028's mechanics clause absorbs the names chosen here; ADR-0012's predicate-in-code becomes the Environment FK.

9Risks and numbers

  • Size: fifteen waves, ~6,000 lines total by the per-wave estimates above (each marked estimate; firmed per wave by the brief). Phase 1 landed eleven waves; this is the same order of magnitude with a front end in it.
  • The widest blast radius is E0/E1: eleven tables re-policied and the Scope triple threads through work, tick, serve and every test fixture. Mitigation: the rail is three cut waves with the suite green between each, and the 23-table list lives in three places the brief names (premise 4's migration, the migration test, ORM metadata) so none drifts.
